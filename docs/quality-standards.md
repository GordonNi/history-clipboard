# 质量、安全与验收标准

## 基本质量要求

- 每个开发阶段结束时项目必须可编译，除非日志明确记录阻塞原因。
- 不提交半成品功能到当前阶段目标之外。
- 新增功能要有对应的手动验证记录。
- 重要逻辑要拆分清楚，避免把监听、存储和 UI 混在一个文件里。

## 测试要求

第一版以构建检查和手动验证为主，核心逻辑逐步补充单元测试。

每个阶段至少记录：

- 执行了什么验证。
- 结果是否通过。
- 如果未通过，阻塞原因是什么。

核心场景：

- 应用启动。
- 菜单栏入口展示。
- 文字记录。
- 图片记录。
- 历史重新复制。
- 删除和清空。
- 搜索。
- 置顶。
- 保存期限清理。
- 暂停记录。
- 开机启动设置。

## 隐私要求

- 所有历史数据只保存在本机。
- 不进行网络上传。
- 不加入分析、追踪或遥测。
- 不记录来源 App、窗口标题、网页地址等额外上下文。
- 清空全部历史时要删除数据库记录和本地图片文件。

## 稳定性要求

- 剪贴板监听不能明显影响系统性能。
- 图片保存失败时不能导致应用崩溃。
- 数据库操作失败时要保留可恢复状态。
- 长文本和大图片不能撑坏 UI。
- 应用重启后数据和设置要保持一致。

## UI 验收要求

- 主界面简洁直观。
- 淡蓝色是主要强调色，但不大面积刺眼。
- 搜索、置顶、删除、设置入口容易找到。
- 按钮和文字不重叠。
- 空状态和无搜索结果状态清楚。
- 最终手动验收步骤记录在 `docs/manual-acceptance.md`。

## 开发日志要求

每天使用 `dev-logs/YYYY-MM-DD.md`。

每次开发结束必须更新：

- 已完成。
- 待办。
- 问题。
- 下一步。
- 验证记录。

## 变更控制

- 需求变化更新 `docs/requirements.md`。
- 技术方案变化更新 `docs/technical-architecture.md`。
- UI 变化更新 `docs/design-guidelines.md`。
- 开发步骤变化更新 `docs/development-plan.md`。
- 质量规则变化更新 `docs/quality-standards.md`。
